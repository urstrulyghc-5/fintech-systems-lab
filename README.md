# FinTech Systems Lab — Payment Processing Prototype

An educational, browser-based simulation of application-level payment processing. It demonstrates request validation, simulated authorisation outcomes, transaction states, duplicate-request protection, internal ledger and settlement records, event trails, and reconciliation.

## Important scope statement

This is a **simulation only**. It does not connect to UPI, banks, card networks, wallets, payment gateways, or any live financial infrastructure. All merchants, transactions, authorisation outcomes and settlement records are fictional. It must not be presented as a production payment service.

## Run the interface

You can publish this static site with GitHub Pages. In the repository settings, select **Pages**, choose deployment from the `main` branch and `/ (root)`, and save. Open the published URL after GitHub finishes deploying.

For local development, serve this directory over HTTP rather than opening `index.html` as a `file://` URL, because the app uses JavaScript modules. For example, if Python is installed:

```bash
python -m http.server 8000
```

Then open `http://localhost:8000`.

## Run automated tests

Requires Node.js 20 or later. In the project directory run:

```bash
node --test
```

The tests cover request validation, successful processing, declines, timeouts, duplicate request keys, and reconciliation exceptions.

## Implemented behaviour

- Validate merchant reference, positive amount, amount limit, supported simulated rail, request key and scenario.
- Represent successful, declined, pending-review and validation-failed outcomes separately.
- Reject reuse of an idempotency/request key in the engine.
- Avoid automatically retrying a timed-out transaction whose outcome is uncertain.
- Create matching internal ledger and simulated settlement records only for successful scenarios.
- Compare successful transactions' ledger and simulated settlement records and report exceptions.
- Keep a timestamped event trail for each simulated transaction.

## Known limitations

- State and records live only in the current browser session and reset on refresh.
- The app is not a regulated payment system, a real payment gateway, or a financial ledger.
- The timeout, authorisation, settlement and rail behaviour are simplified educational scenarios, not claims about a specific provider's production implementation.
- The duplicate-request guard is in-memory for this prototype. Production systems need durable idempotency storage, concurrency controls, authentication, access controls, secure logging, monitoring, risk controls, and provider/network-specific integrations.
- The settlement dataset is generated by the simulation, not imported from a bank or payment provider.
